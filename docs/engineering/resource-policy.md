# Transport contracts and resource policy

This branch strengthens the existing ports/adapters rather than adding a second framework. Python aliases and wire command/topic names remain unchanged. Go2 is still the only locally supported model; Remote signaling and G1/R1 support are not implemented or physically validated.

## Responsibilities and ownership

- `datachannel/core/framing.rs` parses both binary headers once; routing and LiDAR decoding consume the parsed result.
- `datachannel/core/chunks.rs` owns ordered, bounded chunk assembly, duplicate/conflict handling and expiry. The service owns request correlation and session reset; the assembler does not send messages or invoke Python.
- Connection orchestration owns serialized reset/connect/validation/rollback, including cancellation. An armed attempt retains the owned session gate until asynchronous rollback finishes, so late cleanup cannot close the next attempt; the RTC adapter owns bounded outbound work and its sender task. Queue acceptance is **not** send completion or a robot acknowledgement.
- The session/resource owner belongs to private `connection/session.rs`; connect/validation/rollback/shutdown helpers belong to `connection/lifecycle.rs`. Python bridges marshal API calls rather than duplicating that policy. Disconnect invalidates active and already-queued connection attempts; validation observes the same cancellation signal. The connect transport attempt has a 15 s deadline, HTTP requests 10 s, and HTTP bodies a 1 MiB ceiling before text/base64/decryption/JSON processing.
- Public `connection::UnitreeSession` assembles and owns the same lifecycle, routing, queues, LiDAR workers and audio policy for every native binding. `new` uses existing HTTP/RTC adapters; `with_adapters` injects offline/custom ports. Both return `(session, EventReceiver)`; the consumer owns event processing and must keep the receiver alive while using events. The protocol event channel owns captured epochs, count/byte admission and dispatch permits.
- Python children and their asynchronous operations retain the complete session owner. Await `disconnect` for deterministic transport teardown; final drop stops core work and schedules best-effort close on the last active Tokio runtime, which must still be running. Raw Rust datachannel handles retain resources but do not independently own a validated session.
- Router/heartbeat workers do not keep the external connection owner alive. Epoch checks invalidate old heartbeat work on reset. Each heartbeat has an interruptible two-second wait: stop/reset/fault closes its epoch-local cancellation channel, so idle workers can release their resources without waiting for the next live tick. The live cadence is unchanged; router owner polling and eventual worker scheduling remain distinct from an async join guarantee.
- FFI validates user inputs/callables and translates errors. It releases registry locks before invoking Python and emits redacted conversion/invocation diagnostics.
- Codecs own decoding and buffers; video handles the negotiated BGR plane offset/stride instead of assuming tightly packed GStreamer memory.

Ingress carries a generation captured when its peer handler is created. Router processing, request registration/enqueue, subscription mutation and reset share a synchronization boundary. The sender worker checks its captured epoch before each queued send. Stale validation/heartbeat/chunk/response payloads cannot mutate the new core session. A terminal send fault is retained independently of ingress queue capacity and is checked before each router iteration, including after an idle wait of up to 100 ms, rather than waiting for response timeout. Scheduling, parsing and lock contention add latency; this is not a real-time completion deadline. Queue acceptance is still not wire completion or robot ACK; already-started sends cannot be recalled.

Callback producers capture the same epoch at ingress, peer creation or LiDAR job submission. Old work cannot be relabeled with the current epoch. The receiver drops stale envelopes; Python retains the envelope/byte permit through attachment/conversion and checks again immediately before callback admission. No lifecycle/registry lock is held across user code. An already-admitted callback may complete after reset; disconnect does not forcibly cancel user Python code. Peer/media/command cleanup is owned and tracked from early peer setup; canceled teardown waiters do not cancel the stored cleanup worker, and later close/prepare calls await that completion. A live Tokio runtime and eventual upstream close completion remain prerequisites.

Audio playback retains its sender or an owned cleanup task in the session. Async stop/reset/disconnect offload native pipeline shutdown and bus-thread joining, then observe both native cleanup and aborted RTP-task completion. Canceling the waiter retains cleanup ownership and the session gate until cleanup finishes; a later operation cannot overtake it. This does not impose a hard deadline on a hung native operation. Low-level Rust `AudioSender::stop` remains synchronous/blocking; final `Drop` is best effort, not the explicit session shutdown guarantee.

### Explicit Python callback release

`conn.clear_callbacks() -> None` synchronously takes the current registry under its lock, then releases Python references while attached, **outside** that lock so finalizers can reenter. It releases topic, LiDAR, audio and video registrations only. Disconnect/reconnect retain registrations for reuse; clear does not disconnect, unsubscribe remotely, disable media, close the session permanently or provide automatic cycle collection. An already-copied/admitted callback may finish, and finalizers may register new callbacks before clear returns. Later registration remains valid. Use explicit release to break callback/owner reference cycles; user-retained arrays remain user-owned.

## Public session options

`SessionOptions::new(method, ip)` retains local ingress/control-event capacities 256/64 and Remote 512/128 (Remote signaling is still unsupported). Media callbacks use a separate count quota `min(event_capacity, 4)` and a 32 MiB accounted buffer budget; control/topic callbacks have a 2 MiB accounting quota. The validation timeout defaults to 5 s; LiDAR workers default to available CPUs clamped to 2–4. Explicit options validate positive, clock-representable timeout and capacities/workers before queue/pool allocation: ingress 1–4,096, events 1–256, workers 1–32. These are safety ceilings, not recommended fleet sizing or robot maxima. Invalid options fail before the adapter factory is called. `connect`, `reconnect`, `disconnect`, retries and concrete audio playback share the Rust lifecycle owner; retry backoff is outside its gate so disconnect can proceed.

## Named safety policies

These are conservative **software resource ceilings**, not Unitree protocol constants or measured robot/firmware maxima. Oversized or malformed inputs are rejected. Codec/reassembly ceilings are not exposed as additional tuning APIs; session queue/worker/timeout options are described above. No unverified per-model override is introduced; revise a policy with sourced fixtures and memory/latency evidence when an actual workload requires it.

| Boundary | Policy | Owner |
| --- | --- | --- |
| One chunked transfer | Up to 4,096 chunks and 16 MiB; one-based indexes; identical duplicates are idempotent, conflicts invalidate assembly | `core/chunks.rs` |
| Retained chunk state | Up to 64 transfers and 64 MiB aggregate, 30 s non-sliding deadline; reset/expiry/request cleanup removes state | `core/chunks.rs`, service |
| Ingress text/JSON | 1 MiB input checked before parsing; 65,536 value/key visits (including duplicate keys), 64 containers, enforced while building the owned JSON tree in one pass | `protocol/ingress.rs`, RTC handler, core service |
| Binary ingress | 1,152 KiB per frame, 64 KiB JSON header; reject before framing/header parsing | `protocol/ingress.rs`, `core/framing.rs`, service |
| Binary result expansion | Up to 1 MiB raw bytes before expansion to a JSON byte array, including completed chunk transfers; known excess fails the matching pending RPC without a partial result | Core service |
| Outbound command queue | Up to 128 queued commands, 1 MiB serialized command; full/closed/oversized enqueue returns an error | RTC adapter |
| Pending RPCs | Up to 128 registered requests; excess fails before enqueue; cancellation/reset/timeout release admission | Core service |
| Callback admission | Control count configured 1–256 and 2 MiB accounted payload; media count at most 4 and 32 MiB accounted buffers; independent control-first output selection | `protocol/events.rs` |
| LiDAR work queue | Up to 4 pending compressed jobs; generation captured at submission | LiDAR service |
| LiDAR | Up to 1 MiB bitmap, LZ4 worst-case compressed size, 1,000,000 output points; exact three finite origin values and positive finite resolution | `lidar/codec.rs`, service |
| H.264 | Up to 8 MiB per NAL; runtime FU-A requires next sequence (including wraparound) and unchanged timestamp; loss/duplicate/reorder/conflicting fragments reset assembly; unsupported aggregation modes are rejected | `video/h264_rtp.rs` |
| Encoded H.264 queue | Up to 64 queued buffers and 8 MiB before push; overflow is a sticky terminal stream failure, not blind NAL dropping | `video/codec.rs` |
| BGR video | Up to 64 MiB plane/output; checked geometry, valid offset and positive stride | `video/codec.rs` |
| Python JSON input | 16,384 expanded values including root; 1 MiB accounted value slots, key headers and copied UTF-8/key bytes; 64 containers; active-path cycles/nonfinite floats rejected | `interface/utils.rs` |
| Timeouts | Finite/nonnegative, representable `Duration` and deadline, validated before registration or sending | shared core validation + FFI |

Ingress still mixes control and telemetry; output callback priority does not guarantee input delivery. The event quota charges media `Vec` capacities and conservatively estimates JSON/key storage; it is not byte-exact allocator accounting. Permits remain charged while a Python delivery is dispatch-owned, including dequeue/attachment waits. Public Rust `recv` transfers ownership and releases the permit; user-retained Rust buffers/NumPy arrays, decoder working memory and allocator overhead are outside the quota. Failed enqueue, stale discard and receiver drop release permits; reset never zeroes a counter for still-live buffers. These ceilings do not establish a whole-process/fleet RSS budget, real-time deadlines or reliable robot command delivery. The SDK does not implement a general latest-frame/coalescing policy.

Ingress has per-message checks and a count-bounded queue, **not an aggregate ingress byte quota**. The locked `webrtc` 0.17.1 callback already has a 65,535-byte receive buffer; the current concrete callback is not unbounded wire input. This does not bound all upstream reassembly or other adapters. Custom ports own admission **before** allocation/enqueue: service-side parsing cannot police memory already retained by a custom `Sender<IngressMessage>`. A 1 MiB raw byte array can expand to much larger JSON value storage. The 16 MiB chunk-assembly ceiling is distinct from the 1 MiB final JSON-expansion ceiling; not every admissible assembled transfer is an admissible result. Oversized whole frames are rejected before correlation, so they do not guarantee an immediate request-specific error.

JSON parsing charges each value and key before constructing it, including overwritten duplicate keys, without a separate preflight traversal. A late syntax or budget error can discard a bounded partial tree; this is not a promise of zero allocation before rejection. Strings and keys remain owned for asynchronous consumers, with the same last-key-wins and numeric semantics as the locked `serde_json`. Media buffer ownership and NumPy conversion are separate and unchanged.

Python conversion charges repeated shared containers on every expanded occurrence; small repeated noncycles remain valid. Accounting excludes allocator/container overcapacity, Python input/cache memory and arbitrary user-defined conversion work. Supported integer values remain exact across Python/JSON within `[-2**63, 2**64-1]`; larger Python integers raise `ValueError` instead of silently rounding through a float. Serialized command/envelope limits apply separately.

Local HTTP signaling accepts a host, not a URL: IPv4, IPv6 and strict ASCII DNS labels are assembled structurally into endpoint URLs. Ports, paths, userinfo, query/fragment injection, escapes and ambiguous numeric hosts are rejected with fixed errors. LAN HTTP remains supported, but environment/system proxies and redirects are disabled. Response-topic mismatch diagnostics are fixed text rather than peer-supplied topics. These are intentional admission/redaction changes, not additional model support.

## Compatibility and buffer contracts

- Python receives LiDAR `float32 (N, 3)`, video BGR `uint8 (H, W, 3)`, and interleaved audio `int16 (samples,)` arrays. Opus decoding retains the configured rate/channel metadata internally; the legacy Python callback still receives only its sample array.
- `Vec` → NumPy ownership transfer is zero-copy at that boundary; retained arrays outlive the Rust event. Network parsing, decompression, codec output and stride repacking can still allocate/copy. No end-to-end zero-copy, GIL-free callback or speedup claim is made.
- The root `unitree_webrtc_rs.pyi` is the Maturin-shipped stub. The unused, unshipped `python/unitree_webrtc/types.py` helper and duplicate `python/unitree_webrtc_rs.pyi` were removed. Source-path consumers must migrate to the root stub and native exported constants; no duplicate Python command catalogue is maintained.
- Existing Python unit futures (`connect`, `disconnect`, `reconnect`, audio `play_from_file`, `play_from_url`, `stop`) resolve to `()`, not `None`; the shipped stub reflects that existing behavior. Dictionary/boolean-returning APIs are unchanged. The extension and legacy driver explicitly declare GIL use; free-threaded operation is not supported or validated. This is a support-policy opt-out, not evidence of a discovered race.
- **Rust event API migration:** use `protocol::events::event_channel(capacity)?`, `EventSender`, and `EventReceiver` instead of raw crossbeam callback channels. Session return/factory, RTC/media constructors and LiDAR pool signatures use these wrappers. `CallbackEvent` variants and Python callback values are unchanged. Producers capture `sender.for_generation(epoch)`; LiDAR requests carry `generation`. Native receivers retain `recv`, `try_recv`, `recv_timeout`; the wrapper does not emulate all crossbeam APIs or implement Clone. `DcMessage::TransportFault` is local-only and custom exhaustive matches must handle it; `DataChannelPort::take_transport_error` defaults to no fault for existing adapters.
- **Rust source API change:** exported `datachannel::lidar::bits_to_points_optimized` now returns `Result<Vec<f32>, String>` instead of `Vec<f32>`. Rust callers must handle/propagate rejection. Python imports, aliases and valid output shape/dtype are unchanged; no silently empty compatibility wrapper is provided. Rust `ConnectionService` operations require a Tokio runtime and owned (`'static`) transports for cancellation cleanup. Async teardown still requires that captured runtime to stay alive until cleanup completes.
- **Fallible startup:** `LidarWorkerPool::try_new(events, worker_count) -> Result<Self, String>` validates 1–32 workers; `DataChannelService::try_new(...) -> PortResult<Self>` and Python-feature `interface::callbacks::try_spawn_callback_dispatcher(...) -> Result<(), String>` return sanitized thread-start errors. Existing low-level `new`/`spawn_callback_dispatcher` entry points retain their signatures and documented panic-on-startup-failure behavior. High-level `UnitreeSession::new`/`with_adapters` propagate startup errors and observe already-started idle LiDAR workers on failed construction only; normal pool drop remains nonblocking. Python construction raises `RuntimeError` on dispatcher-start failure and releases the newly assembled owner without starting a connection.
- **Internal RTP path:** runtime media uses additive `H264RtpReassembler::process_rtp_packet(payload, sequence_number, timestamp)`. The retained `process_packet(payload)` helper remains payload-only and cannot check continuity; do not mix the two paths within one fragmented NAL. Timestamps may change between complete NALs; this private module is not a new exported Rust API.
- **Rust adapter migration:** ingress producers/receivers now use `IngressMessage { generation, payload: DcMessage }`, including `RtcEngine::new`, `DataChannelService::new` and `DataChannelPort::set_message_sender`. Implement the required fallible `set_ingress_generation` method and capture that generation by value when each peer handler is created; do not read a mutable current generation when an old callback delivers a message. `DcMessage::for_generation` wraps payloads without changing robot wire data. Unsupported generation setup must fail before offer preparation. `RtcReadyState` also adds `Disconnected`/`Failed`; exhaustive Rust matches must handle them. Low-level `ConnectionService` denotes transport establishment, while `UnitreeSession::is_connected` requires peer validation too.
- Unsafe or ambiguous inputs previously truncated, panicked or silently converted may now raise `ValueError`/`TypeError` or return a Rust error. This is an intentional trust-boundary tightening.

## Test and release tooling

Default Rust tests enable `python` and link Python; extension builds enable `extension-module`, which implies `python`. With `default-features = false` / `--no-default-features`, PyO3/NumPy/async bindings and Python build helpers are absent, and `build.rs` does not resolve an interpreter. `make test-core` verifies the graph, strict Clippy, checks and tests for this path. Native crypto constructors initialize a provider independently of Python import and preserve a provider already selected by the host.

For Python builds, `build.rs` uses upstream PyO3 linker helpers for the relevant target instead of applying Darwin flags to every test. An empty framework prefix (uv Python) must not generate an empty rpath. `make test-rust` supplies the interpreter base prefix and virtualenv package directory for relocated/embedded-Python NumPy tests.

Use `make init` for an initial development environment, or `uv sync --locked --dev --no-install-project` followed by `make build`. `make test-python` depends on a fresh native build and explicitly selects SDK `pyproject.toml` so a parent repository's pytest configuration cannot leak in; `make acceptance` runs guidance/check/core/Rust/fresh-native checks in order. A Makefile invocation serializes Cargo operations even under `make -j`; unrelated concurrent make processes are not covered. Native tests require the actual extension loader and are not allowed to silently skip in favor of mocks. `make wheel-smoke WHEEL=...` installs into a fresh temporary environment outside the repo and runs native offline contracts there. The reusable PR/branch acceptance workflow also supplies release builds after version/tag preflight; configuration is not remote CI success, and recorded artifact hashes/tool versions are not signed attestations or reproducible-build proof. See [contributor measurement instructions](../../CONTRIBUTING.md#offline-measurements) for the bounded benchmark.

The version script updates the two project manifests and both locks, preserving unrelated fields and rolling all four files back on failure. `make deploy` uses locked builds but does not publish. Review dependency/version diffs before distributing; the project remains Proprietary and upstream notices/licensing need a separate release decision. See the [publishing guide](../../.github/PUBLISHING.md) for the configured matrix, authentication and release gates.
